# Commercial MVP checklist

This checklist shows what is already mature, what blocks a real commercial launch, and the safest order to continue Desktop Pet Companion.

## Current product foundation

| Area | Status | Evidence |
| --- | --- | --- |
| Desktop overlay app | Done | Tauri app with overlay, tray/menu controls, local state, activity points, skins, and pet library. |
| Local pet import | Done for development | Folder import, native picker, `.petpack`/`.zip` import, collision confirmation. |
| Petpack v2 structure | Done | `manifest.json`, `petpack.json`, `license.json`, `signature.ed25519`. |
| Petpack integrity | Done | SHA-256 runtime asset validation. |
| Petpack authenticity | Done for dev/MVP path | RFC 8785/JCS canonical payload + Ed25519 verification. |
| Account binding | Development bridge | App exposes `user_test`; license subject must match before install. |
| Dev petpack generation | Done | `npm run petpack:dev -- <source_dir> <output.petpack> <account_id> ...`. |
| Dev/prod import boundary | Done | Dev imports hidden/rejected unless dev flags are enabled. |
| Landing/store skeleton | Done | Static Spanish-first web skeleton under `web/`. |
| Store API contract | Drafted | `services/store-api/openapi.yaml`. |
| Manual E2E validation | Done in current dev session | Valid import, replace/cancel, wrong-account rejection, tampered-asset rejection, and friendly error messages were manually verified. Re-run checklist before release. |

## Commercial launch blockers

These must be addressed before selling pets publicly.

| Priority | Blocker | Why it matters | First done condition |
| --- | --- | --- | --- |
| P0 | Production signing key management | The private key must live server-side only and stay outside the repository. | App uses the production public key; generator/backend signing comes from local/server secrets, never committed code. |
| P0 | Real account/auth session | `user_test` is only a placeholder. Licenses need real user identity. | Desktop app can sign in and expose current account id from auth provider. |
| P0 | Entitlement backend | Store must know who owns which pets. | Backend can create/read entitlements and reject unauthorized downloads. |
| P0 | Server-side petpack generation | Commercial petpacks must be generated by the backend, not local dev tooling. | Download API emits signed account-bound petpacks using server key. |
| P0 | Installer distribution | Users need trustworthy app downloads. | Windows/macOS installers exist and are linked from web. |
| P1 | Real payment integration | Purchases must create entitlements reliably. | Payment webhook creates/updates entitlement records. |
| P1 | Minimum app version enforcement | Petpacks declare `minimumAppVersion`, but current code only checks presence. | App rejects petpacks requiring a newer app version and shows clear update copy. |
| P1 | Production import policy | Release builds must reject dev imports and dev keys. | Production build accepts only signed licensed petpacks from production trust root. |
| P1 | Download abuse controls | Public downloads need rate limiting and audit logs. | Download endpoints record audit events and enforce reasonable rate limits. |
| P1 | Supportable error states | License/account/signature/hash failures need clear copy and support paths. | UI and docs explain common failures in Spanish. |

## Nice-to-have after MVP

Do not block the first private/beta commercial test on these unless they become urgent.

- Direct `download/open in app` flow from the store.
- Soft periodic revalidation for installed pets.
- Revocation strategy.
- Device-bound licenses.
- Advanced analytics/audit dashboard.
- Full i18n (`es`/`en`).
- In-app catalog browsing.
- Automated UI tests for import flows.

## Recommended implementation order

### 1. Replace dev key with production-key configuration

Goal: stop relying on the RFC/test-vector key before public builds.

- Add production public-key configuration in the desktop app.
- Keep dev/test key only behind development configuration.
- Document key rotation basics.
- Add tests proving dev and production trust roots are not accidentally mixed.

### 2. Add real desktop account session

Goal: replace `user_test` with authenticated account identity.

- Choose auth provider.
- Implement browser login/callback or equivalent desktop auth flow.
- Store tokens securely through OS credential storage.
- Expose current account in the UI.
- Compare `license.subject.id` against real account id.
- Decide explicit logout/account-switch behavior for already-installed pets.

### 3. Build minimal store backend

Goal: make catalog and ownership executable before paid downloads.

- Implement `GET /pets`.
- Implement `GET /me/library`.
- Use a mock/manual entitlement store first if payment is not chosen yet.
- Do not expose `POST /downloads/pets/{petId}` until server-side petpack generation is ready.

### 4. Move petpack generation server-side

Goal: produce real commercial petpacks through the download API.

- Reuse generator logic server-side.
- Sign with private production key.
- Generate `license.json` from entitlement and account.
- Implement `POST /downloads/pets/{petId}` and `GET /downloads/{downloadId}`.
- Return a short-lived download URL.

### 5. Add payment provider

Goal: users can buy pets.

- Pick provider.
- Implement checkout start.
- Verify webhooks.
- Create entitlements after successful payment.

### 6. Prepare release distribution

Goal: users can install the app safely.

- Windows signing path.
- macOS notarization path.
- Landing download links.
- Basic release notes and versioning.

## Current development workflow

Generate a valid dev petpack:

```bash
npm run petpack:dev -- ./public/pets/demo ./tmp/chimmy-v2.petpack user_test ent_chimmy lic_chimmy
```

Run the app:

```bash
npm run tauri dev
```

Manual validation checklist to re-run before release:

- [ ] valid `user_test` petpack imports;
- [ ] duplicate import asks before replacing;
- [ ] cancel does not replace;
- [ ] wrong-account petpack is rejected;
- [ ] tampered asset is rejected;
- [ ] user-facing error message is understandable.

## Decision reminders

- Product-facing language starts in Spanish.
- Code, APIs, manifests, filenames, and commits stay in English.
- Web/store is in the same repository for now.
- Purchases happen on the web, not inside the desktop app for MVP.
- Installed pets should keep working offline after successful validation.
- Perfect DRM is not the goal; reasonable protection and good UX are the goal.
